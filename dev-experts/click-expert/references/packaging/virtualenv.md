# Virtualenv

Docs: https://click.palletsprojects.com/en/stable/virtualenv/

```console
$ mkdir myproject && cd myproject
$ python3 -m venv .venv
$ . .venv/bin/activate          # Windows: .venv\scripts\activate
$ pip install click
$ pip install -e .              # once pyproject.toml exists
$ deactivate
```

Why it matters here specifically: the entry-point wrapper generated by
`[project.scripts]` (`entry-points.md`) is written into the environment's `bin`/`Scripts`
directory. Installing into the system Python either fails on a managed install or scatters
executables outside your control; installing into a virtualenv puts the command on `PATH`
exactly while that environment is active.

For an end-user tool, `pipx install <package>` (or `uv tool install`) does the same thing
without asking the user to manage an environment.

## Common Anti-Patterns

- `sudo pip install .` → installs the wrapper system-wide and can break OS packages.
- Forgetting to reactivate after opening a new shell, then reporting "command not found".
- Installing the dependency but not the project → `pip install click` alone does not create
  your executable; `pip install -e .` does.
